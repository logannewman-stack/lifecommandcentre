# Life Command Center (CLAUDE.md)

Logan's personal productivity web app, for one user only. It is not a product: no billing, no multi-tenant features, no marketing pages.

## Stack
- Vite + vanilla JS (no framework). Entry: `index.html` → `src/main.js`. Fonts are self-hosted from `@fontsource` (latin subsets only). Pure helpers with no DOM live beside it so Node can test them: `src/quickadd.js` (smart add parser), `src/planday.js` (Build my day) and `src/outreach.js` (the pipeline rules, heat, lead import, email campaigns and the engine's email rules).
- Supabase: email/password auth (one user, sign-ups disabled) and Postgres. `src/supabase.js` reads `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` at build time, or values saved on the device from the in-app Connect screen when the build has none.
- Hosted on Vercel (Vite preset, `vercel.json` sets caching headers). Pushes to the production branch deploy automatically. `.github/workflows/build.yml` runs the build on every push.
- PWA: `vite-plugin-pwa` (`vite.config.js`) generates the manifest and a Workbox service worker that precaches the app shell. Supabase requests are never cached by the worker. Update mode is `prompt`: `main.js` shows a "new version ready" toast, and a waiting worker also takes over on the next cold start. `public/` holds the icons; regenerate them with `npm run icons` (`scripts/icons.mjs`, needs Playwright).

## Data model
- One table, `public.docs`, with columns (owner uuid, collection text, id text, data jsonb, updated_at). RLS restricts every row to `auth.uid() = owner`. Schema is in `supabase/schema.sql`, which also installs `patch_doc(collection, id, patch)` (server-side deep merge) and a trigger that sets `updated_at`. It is idempotent.
- `src/db.js` wraps it in a Firestore-style API: `db.collection(c).onSnapshot(fn)` and `db.collection(c).doc(id).get/set/update/delete`. Keep this API stable; `main.js` depends on it. It is offline-first:
  - rows are cached in memory and mirrored to `localStorage` (`lcc:cache:<uid>`) so the app paints instantly and reads offline;
  - writes update memory first, then join a persisted queue (`lcc:queue:<uid>`) that is sent in order, batched for sets, and retried on `online`, on visibility, on a backoff timer and every 5 minutes;
  - `update()` sends a patch to `patch_doc` and falls back to fetch + merge + upsert if the function is missing (`PGRST202`);
  - Realtime events are ignored for documents with queued writes and when older than the version held; every reconnect and visibility change triggers a full reload;
  - `db.status()` feeds the header sync chip; `db.refresh()`, `db.flush()`, `db.destroy({wipe})` exist. Sign-out wipes the local copies.
- Collections:
  - `config/schedule`: `{days: {Mon: [item…], …}}`. An item is `{key, start "HH:MM", end, tag, text, kind, carry?, quota?, region?, minutes?, sessionType?, hours?, short?, area?}`.
    - `kind` is one of `marker | task | checkin | checkout | calls | session | gym | mobility | watch | dupr`.
    - Keys repeat across weekdays for the same block (`checkin`, `drill`, …). Blocks added in the app or by the assistant get `b<base36>` keys.
  - `config/roadmap`: `{weeks: [{start "YYYY-MM-DD", focus, musts}]}`.
  - `config/profile`: move date, start/goal weight, DUPR start and checkpoints, weekly targets, the Dec 1 gate, links, `startDate`, `restDays` (defaults to `['Sun']` when missing).
  - `config/money`: account balances, history, and the weekly savings plan.
  - `days/<YYYY-MM-DD>`: `{date, off?, checks{key:bool}, skips{key:bool}, moves{key:{start,end}|null}, am{weight, sleep, energy, top3[{t,done}], note, savedAt}, pm{…, savedAt}, calls[{t, id, name, region, kind, outcome, dial, convo, demo, dm}]}`. `moves` are one-off times for that date only; `null` means back to the usual time. `off: true` makes that date a day off (treated as a rest day everywhere).
  - `tasks/<id>`: `{title, due, origDue, area, notes, done, doneOn, dropped, kind: task|makeup|top3|fix|sales}`.
  - `leads/<id>`: every business, called or emailed, is one lead (the CRM). `{name, type: Cold|Warm|Client|Partner, stage, stageAt, history:[{at, from, to, by}] (last 25), nextStep, nextDate, callList, phone, email, firstName, business, contact, website, city, state, kind, segment, region: IA|AZ|'', source: Finder|Import|Manual (none = the original call list), foundAt, confidence, touches, lastTouch, notes, deal, monthly, collected, dnc?, emailBad?, reply?:{label, at, summary}, seq?, sentLog:[{at, campaign, step, id}] (last 30), threads (last 10), enrolled:{<campaign>: date}}`.
    - `stage` is one of `STAGES` (`New lead, Contacted, Talking, Demo booked, Proposal sent, Won, Not now, Lost`); `history.by` is `you | call | reply | email | finder | import | manual`.
    - `callList` (missing means true) puts a lead on the Calls list on its `nextDate`; found and imported leads start off it, and a hot reply puts them on it for today.
    - `seq` is the lead's place in an email campaign: `{campaign, status: hold|queued|active|done|replied|paused|stopped|bounced, step, nextOn, startedAt, threadId, rfcId, lastAt, sendingStep, sendingAt, failCount, lastError, pausedWhy, stoppedWhy}`. `enrollPatch` sets every key so a merge replaces the old one.
    - Ids: the original call list keeps its slugs, manual adds are `lead-<base36 time>`, imported and found leads are `e-<email slug>` (`leadIdFor`).
  - `sessions/<id>`: pickleball sessions. `auto-<date>-<key>` ones are created when a drill or play block is checked off.
  - `dupr/<date>`, `weeks/<weekStart>` (Sunday review: leak, fix), `meta/rollover` (`{through, freshStart?}`), `meta/setup` (one-time runs: `{freshStart, restart, at, restartAt, version}`).
  - `push/<deviceId>`: Web Push subscription for one device `{endpoint, keys, tz, lead, enabled, ua}` (written by the app). `pushlog/<deviceId>`: `{sent: {"<date>|<key>": ts}}` written only by the reminders function.
  - `events/<id>`: one-off items for a single date `{title, date "YYYY-MM-DD", start "HH:MM", end, where, notes, kind?, sessionType?, tag?, quota?, region?, from?: {date, key}, createdAt, updatedAt}`. No `kind` (or `event`) is an appointment; otherwise `kind` is `session | task | gym | mobility | watch | calls | marker`; court time carries `sessionType`, call blocks `quota`/`region`. `tag` overrides the computed label; `from` marks a weekly block moved here from another day. Ids are `ev-<base36 time>` (the assistant uses the same shape).
  - `chat/main`: the assistant conversation `{messages: [{role: user|assistant, content, at, actions?: [string]}]}`, kept to the last 40 messages, shared by every device.
  - Email outreach (see Email outreach below):
    - `outreach/settings`: `{enabled, autoStart, startOn, address, forwardTo, fromName, website, days, start, end, tz, capStart, capStep, capMax, gap, startedOn?, finder:{enabled, perDay, budget, model, review, targets:{<campaign>:{on, niches, areas}}}}` (`withDefaults` fills the rest from `DEFAULT_SETTINGS` and `FINDER_DEFAULTS`). The engine skips an account without it; the app writes `{enabled:false}` once (`maybeSeedOutreach`). Sending is on when `enabled` (Start sending now) or `autoStart` (set by the Start sending sheet) is true, and either waits for `startOn` when it is set (`sendingState`: `paused | later | on`, a shared rule); `startedOn` is the first day an email went out (the warm-up counts from it). The address is a line of text in the footer (CAN-SPAM); nothing is ever mailed, and the app suggests a PO box or virtual mailbox.
    - `outreach/state`: written only by the send job `{lastRun, lastError, lastWhy, version, gmail, today:{date, sent, by:{campaign:n}}, lastSendAt, labels, historyId, pending}`.
    - `outreach/finder`: written only by the finder `{lastRun, lastWhy, lastError, version, today:{date, found, spent, searches, runs, checked, noEmail}, month:{month, found, spent}, done:{<job key>: date}, cursor, recent:[{at, search, campaign, found, checked, cost, names}]}`.
    - `campaigns/<id>`: `{name, status: running|paused, reviewed, reviewedAt, cap, order, offer, price, trigger?:{stage, days}, steps:[{subject (first only), body, wait (follow-ups)}], segments:{<key>:{label, question, features}}}`. Four are seeded from `DEFAULT_CAMPAIGNS`: `home-screen` and `front-desk` (cold), `check-back` (trigger Not now, 60 days) and `proposal` (trigger Proposal sent, 2 days). Only a running and reviewed campaign sends (`liveCampaign`).
    - `replies/<gmail message id>`: `{lead, campaign, business, email, from, subject, text, snippet, at, label, summary, next, by: claude|rules, threadId, handled, forwarded, relabeled?}` (1.9 replies carry `prospect`). Labels: `interested | question | referral | not_now | not_interested | unsubscribe | bounce | auto | other`; the first three are hot (`HOT`).
    - `suppress/<lowercased email>`: `{email, reason, at}`, the do-not-contact list. Imports and the finder skip it and the engine never sends to it.
    - `prospects/<id>` is the 1.9 contact list. `maybeMigrateProspects` (run once from `maybeSeedOutreach`) turns each into a lead or joins it to the lead it came from, points its replies at the lead and deletes it.

## Automations (in main.js)
- **Rollover (`runRollover`):** runs only after the first successful load from the server (never on a stale local copy). It processes each day after `meta/rollover.through`, up to yesterday (max 3 days back, never before `profile.startDate`). It creates make-up tasks for missed `carry` items, dial shortfalls and unfinished top-3 items. Rest days get no schedule make-ups. Task IDs are deterministic (`mk-…`, `t3-…`) so reruns don't duplicate.
- **Rest days (`isRestDay`):** `profile.restDays` or a day off (`days/<date>.off`). On a rest day nothing is marked late or behind (schedule, to-dos and leads), the carried-over section and the Calls badge are hidden and a rest banner shows instead (a day off says "Day off" and has **It's not a day off**, `day-off` with `data-on="0"`). Rollover skips schedule make-ups for both.
- **Restart on Tuesday Oct 6 (`maybeRestart`, right after `maybeAutoFreshStart`):** once, while today ≤ `RESTART_DATE` (2026-10-06) and `meta/setup.restart` is missing, it writes `meta/setup.restart` first, runs `applyFreshStart(RESTART_DATE, false)`, makes Monday Oct 5 a day off and logs Monday's work with `logMonday` (the `drill` and `play` blocks checked off with their `auto-` sessions, the noon court time as a checked one-off or `s-<date>-noon`, the done task `w-<date>-innerboard` and a dated note on the Leah Roling lead), all skipped when already there. Both one-time runs keep an in-memory guard (`autoFreshChecked`, `restartChecked`) because a snapshot can replace `S.data.meta` before the queued `meta/setup` write lands.
- **Automatic fresh start (`maybeAutoFreshStart`, called from `maybeRollover`):** on the first load after `AUTO_FRESH_DATE` (2026-10-05) ships, if neither `meta/setup.freshStart` nor `meta/rollover.freshStart` exists and `profile.startDate` is older, it runs `applyFreshStart(max(today, AUTO_FRESH_DATE), true)` and writes `meta/setup`. Never repeats.
- **Fresh start (`applyFreshStart`, UI in `submit('fresh')`):** moves unfinished older to-dos and lead follow-ups (`nextDate`) to the chosen date, drops `makeup`/`top3` tasks, sets `meta/rollover.through` to the day before, sets `profile.startDate` and optionally `restDays=['Sun']` plus the `REST_SUNDAY` schedule (church 10:30 to 13:00, play 15:00 to 17:00).
- **Build my day (`src/planday.js`, sheet `build`):** `parseDayText(text, today, now)` splits one line on commas, "then" and "and" (only when every part has a time), reads "woke up at 8" / "up at 8" / a short "start at 9" or "free from 2" as the start, and the rest through `parseQuick` → `{start, items, left}` (left: pieces with no time). `buildDay(items, fixed, {start, now})` plans from `max(start, now)` (today) or the start / first block (another day) up to the check-out: what you typed, one-offs already there, done blocks and the check-out stay put; the wake note moves to the start; a meal moves later out of the way (up to 3 h, or 45 min earlier) and a typed meal replaces it; blocks that still fit stay; the rest go to the free slot closest to their time, by `PRIORITY` (check-in, calls, task, session, gym, mobility, dupr, watch), what's still ahead before what was missed; no full slot → the closest gap of at least half (short blocks don't shrink); nothing → canceled (`room`); template court time is canceled (`covered`) when the day has your own court time; notes now inside a block are `hidden`. `applyBuild(date)` writes the new one-offs, `days/<date>.moves` and `.skips` (canceled and hidden), with one undo. `buildPlanFor(date, text)` feeds it `itemsFor(date)` with done/skipped flags.
- **Day off and start fresh tomorrow:** Catch up's footer has `day-off` (`data-on="1"`, sets `days/<today>.off`, with undo) and `fresh-tomorrow` (`applyFreshStart(tomorrow, false)` plus today off).
- **Call outcomes (`outcome`):** count dials, conversations and demos into the day's calls, and move cold leads along the 5-touch cadence (gaps of 2, 2, 3 and 6 days). Booking a demo creates the demo task and a proposal task. Only the changed fields are patched; a stage change goes through `stagePatch(l, to, 'call')`, so a call that reaches the owner stops the lead's email sequence. Undo patches the old values back.
- **The pipeline rules (`src/outreach.js`, repeated in the engine):** `stagePatch` moves a stage, stamps `stageAt`, appends to `history` and stops a live sequence (`LIVE_SEQ`) when the lead moves past Contacted. `replyPatch(l, label)`: interested/question/referral → Talking (not back from Demo booked or Proposal sent; Lost and Not now come back; Won stays), on the call list today, Cold becomes Warm; not_now → Not now; not_interested/unsubscribe → Lost and `dnc`; bounce → `emailBad`; auto → nothing. `heatOf(l)` scores 0–100 from the stage, a reply in the last 30 days and how recent the last touch was: Hot ≥ 60, Warm ≥ 30, Cold, Client (Won), Dead (Lost or dnc).
- **Check-out:** the "fix" becomes tomorrow's task `fix-<date>`.
- **A day's plan (`itemsFor`):** `scheduleFor(d)` with that date's `moves` applied (moved items carry `movedFrom`), plus `eventsOn(d)` mapped by `eventItem` (`key: 'ev-<id>'`, `eventId`, `oneoff: true`, `kind` from the event, tag `EVENT` or the session type), sorted by start. Today, the NOW card, `toggleCheck`, `blockSheet`, calling mode, `dayAuto` and `dayStatsFor` use it, so one-off gym, mobility and study count toward the week and one-off court time logs an `auto-<date>-ev-<id>` session when checked. Rollover keeps using `scheduleFor`, so one-offs never create make-ups. `exportCalendar` appends one-offs as VEVENTs (`eventLines`), `exportEvent(id)` saves a single-event `.ics`.
- **Schedule editing:** `moveBlock(date, key, start, end, scope)` writes `days/<date>.moves` (scope `day`), the weekday's array in `config/schedule` via `patchDoc` (scope `week`, which also clears that date's move), or the event itself. `moveBy`, `moveTime` (Starts/Ends inputs; a new start keeps the length) and `resetMove` build on it. `moveToDay(date, key, toDate)` skips the block on `date` and writes a one-off copy (tag, kind, sessionType, quota/region, `from`) on `toDate`; a one-off just changes its date. Cancel is the existing skip (`skips[key]`), now with undo and a toast. `S.flash = {key, at}` makes the moved row flash for 1.6 s. Adds and edits go through `submit('add')` (one-off event, or a weekly block on the picked weekdays) and `submit('block-edit')` (changed fields copied to every picked weekday; days without the block get a copy). Every change sets `S.lastUndo = {type:'restore', ops}`, replayed by `runOps`.

## Email outreach and the lead finder
- `supabase/functions/outreach/index.ts` is a third Deno Edge Function (deployed by hand as `outreach`, Verify JWT off, secrets `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`, and `ANTHROPIC_API_KEY` for sorting replies with Claude and for the finder). `cron.sql` schedules two jobs: `lcc-outreach` every 10 minutes (the send job) and `lcc-outreach-find` at `7,22,37,52 * * * *` with `?job=find` (the finder). Each run stops itself after about 110 s (`deadline`). FN_VERSION 4 (3 holds every email until `startOn`, and an older engine ignores `autoStart`, so nothing goes out early; 4 keeps the businesses of a cut-off finder answer (`parseFinderJson`) and reports the search it ran).
- The send job (`runOwner`), per account with `outreach/settings`: reads new Gmail messages through the history API (`state.historyId`, unfinished ones wait in `state.pending`), matches them to a lead by thread or by the sender of a lead you emailed (at most 30 metadata checks a run), sorts each with `quickLabel` (bounce, auto-reply, unsubscribe, a flat no), Claude (`classify`, structured output, effort low) or `heuristicLabel`, applies `replyPatch` to the lead, adds `SUPPRESS` labels to `suppress`, stars and labels hot ones `LCC/Hot`, pushes them to the phone (`url: '/#email'`) and forwards them when `forwardTo` is set. Then it starts stage campaigns (`dueEnrollments`: a lead with an email that has sat in a trigger's stage for its days and isn't in another campaign, at most 25 a run) and sends at most one email (`pickNext`: nothing while `sendingState` is paused or later (why `start`), follow-ups due first, campaigns take turns by share of their cap, each business's time zone from its state, the warm-up `dailyCap`, the `gap`; `afterSend` moves New lead to Contacted by `email`). Before sending it claims the slot (`state.lastSendAt`) and marks `seq.sendingStep`, so a crash can't send twice (the app lists stuck ones under Needs a look). Gmail refusing an address twice pauses that lead (`pausedWhy: 'failed'`). Emails are plain text with the footer (name, website, address, opt-out) and `List-Unsubscribe` headers; follow-ups reuse the thread.
- Every engine write to a lead goes through `casUpdate` (compare-and-swap on `updated_at`, retried), so a change you make in the app at the same moment is kept. The app writes leads with `patchDoc` for the same reason.
- The finder (`runFinder`, `?job=find`): when `finder.enabled`, below `perDay` new leads and `budget` dollars today, it takes the next search from `finderJobs` (every niche × city of each target that is on, campaigns interleaved; a search reruns at most every 90 days, `nextFinderJob`) and asks Claude with the web search tool (`claudeFind`: `web_search_20260209`, `max_uses` 4, effort low, `FINDER_PROMPT`) for local businesses with their websites. Businesses already in the pipeline (domain, name + state, email) are skipped; for the rest it reads the email the search found or crawls the homepage and contact pages (`crawlSite`, `extractEmails` with Cloudflare `data-cfemail` decoding), keeps only an address on the business's own domain or a freemail one (`pickEmail`, role addresses first), checks MX (`hasMx`, dns.google) and inserts a lead (`finderLead`: source Finder, off the call list, `seq` queued in the target's campaign, or `hold` when `review` is on). Cost is counted from usage (`usageCost`, `PRICES`) into `outreach/finder`. It never uses Google Places.
- Endpoints: `GET ?status=1` → `{ok, version, gmail:{ok, email, error}, hasKey, lastRun, lastError}`; `POST` the send job; `POST ?job=find` (or body `{"job":"find"}`) the finder; `POST ?test=1&campaign=<id>` with the session token emails a sample lead to yourself; `GET/POST ?u=<token>` is the signed unsubscribe link (it applies `replyPatch(…, 'unsubscribe')` and adds the address to `suppress`).
- The pure logic is between the `// ---- pure logic` markers; `src/outreach.js` repeats the shared rules (between `// ---- shared rules` markers: `renderText`, `composeEmail`, `segmentOf`, `dailyCap`, `stagePatch`, `replyPatch`, `enrollPatch`…) so the app's preview is exactly what goes out and a stage moved in the app follows the same rules as one a reply moves. A Deno test compares the two copies.
- Proving it works before the first day: **Search now** on the finder card (`em-find-now` → `emFindNow`, `POST ?job=find`, then `db.refresh()` and a toast with what it searched and found) and **Send me both as a test** in the Start sending sheet (`lx-test` → `emTestBoth`, `emTest(id, true)` for each cold campaign).
- The Email tab (`viewEmail`): hero (`emHero`: status, "Starts Mon, Oct 12" with what's left to do while armed, today's count against `dailyCap`, Start sending, Pause (clears `enabled` and `autoStart`), problems from `outreach/state`), the setup checklist (`emChecklist`; its first step becomes Update the engine when `emOutdated()`), Hot replies (`emHotRow`: Reply in Gmail, Call, Open the lead, Done), the finder card (`emFinderCard`: on/off, today's count and spend, this month, cost per lead, last searches), Results, a card per campaign (with its trigger), Up next (`upNext`), In your campaigns (`emContactsCard`: `EM_FILTERS` chips, `#em-search`, bulk Queue/Pause/Resume via `emSetStatus`) and Every reply. Sheets: `em-launch` (`emLaunchSheet`, opened by Start sending, the checklist's last step and Today's Pipeline card: the engine's state, the mailing address `#lx-address`, both cold campaigns (`LAUNCH_CAMPS`) with their first email and a finder switch `lx-f-<id>`, the first sending day `#lx-date`; **Approve both and start <day>** (`lx-go`) is Logan's own approval: `launchWrites` in `src/outreach.js` approves the cold campaigns not approved yet, saves the address and the finder switches, and sets `autoStart: true, startOn`, with one undo; it never sets `enabled`), `em-setup` (seven steps, `outreachCheck`; step 7 is DKIM, SPF and DMARC for the sending domain, with copy buttons), `em-settings`, `em-finder` (form `em-finder`, drafts `ef-*`: leads a day, spending limit, model, check-first, each campaign's niches and cities), `em-import` (`parseCSV` → `importLeads`: a row matching a lead by app id, email, website or email domain, or name + phone/state gets the email and the campaign; anyone else becomes a lead off the call list; a `.csv` dropped anywhere opens it) and `em-campaign` (editor with drafts `ec-*`, trigger fields `ec-tstage`/`ec-tdays`, live preview `#em-preview` via `data-emprev`, Save, approve with `emCampaignProblem`, Send me a test, Back to the original wording). Every change has Undo. The Email tab badge counts unhandled hot replies.

## Reminders
- `supabase/functions/reminders/index.ts` is a Deno Edge Function (deployed by hand as `reminders`, Verify JWT off). Every minute (Supabase Cron or `cron.sql`) it loads `push`, `pushlog`, `config`, `days` and `events` rows with the service role, computes each device's local clock from its `tz`, builds the day with `itemsForDay` (weekly plan + that date's `moves` + one-off items) and sends a Web Push for blocks whose start minus `lead` minutes is now (or one minute ago). Untagged markers never nudge; rest days and days off (`days/<date>.off`) only nudge check-in, check-out, sessions and one-off items; checked, skipped and saved items are quiet.
- All three functions export `FN_VERSION` and report it from `?status=1`. The app reads the version in its embedded copy (`fnVersion`) and shows **Update needed** in the setup sheet (and a card in the chat) when Supabase runs an older one. Bump `FN_VERSION` whenever a function's behaviour changes. `?public_key=1`, `?status=1` and `POST ?test=<device>` serve the app. VAPID keys live in `public.push_vapid`, created on first run. The pure logic sits between `// ---- pure logic` markers so a Node test can import it without Deno.
- The app embeds that file and `cron.sql` with `?raw` imports so the setup sheet can copy them. `src/sw.js` shows pushes and focuses the app on tap.
- Calendar export (`exportCalendar`) writes a weekly-recurring `.ics` with a VALARM per block; floating local times, untagged markers excluded. Events from the last week onward are appended as one-off VEVENTs.

## Assistant
- `supabase/functions/assistant/index.ts` is a second Deno Edge Function (deployed by hand as `assistant`, Verify JWT off, secret `ANTHROPIC_API_KEY`). The app embeds it with `?raw` so the setup sheet (`assistantSheet`, three steps, `GET ?status=1` → `{ok, hasKey, model}`) can copy it.
- Request: `POST {message, history, tz, today, now}` with `Authorization: Bearer <session access token>`. The function verifies the token with the anon client (`auth.getUser`), then loads every row of that owner with the service role, builds a text context (`buildContext`: today's and tomorrow's plan with `[key]`s, status and moves, one-off changes for the rest of the week, the weekly plan, to-dos, calls and pipeline, week vs targets, roadmap, money, body, sessions with ids, one-offs for 30 days) and calls `claude-opus-5-5` through `@anthropic-ai/sdk` (`client.beta.messages.create`, beta `server-side-fallback-2026-07-01` with `fallbacks: "default"`, `output_config.effort: "medium"`, system prompt cached). The prompt tells it to rebuild a day the way Build my day does when Logan describes how the day is really going. The context's call list leaves out leads off the call list, and an EMAIL OUTREACH line gives sending, the finder and the hot replies to answer with their lead ids (FN_VERSION 6). Manual tool loop, at most 8 rounds; handles `tool_use`, `pause_turn` and `refusal`. The context is built once per question: the system prompt must stay byte-identical across rounds or the thinking blocks passed back stop being valid. Response `{reply, actions, version}`.
- Tools (`runTool(store, name, input, today, d)`, all between the `// ---- pure logic` markers so a Deno test can run them on the seed with an in-memory store): `move_block` (with `to_date` to move a block to another day the same way the app does), `skip_block` (cancel), `set_day_off` (`days/<date>.off`; the context marks days off for today, tomorrow and the week), `check_block` (logs the auto session for court time), `add_event` (with `kind` / `session_type` / `label`), `update_event`, `edit_weekly_block`, `add_weekly_block`, `remove_weekly_block`, `add_task`, `update_task`, `add_lead_note` (patches only the note and next step on the current row), `log_checkin`, `log_session`, `log_dupr`. Writes read the current row first and merge (`merge` mirrors `patch_doc`), so a change made on a phone (or by the email engine) a moment earlier is kept.
- In the app: `askAssistant(text)` appends to `chat/main`, posts, stores the reply with its `actions` and calls `db.refresh()` when something was written. `chatSheet` (modal `chat`) has suggestion chips, dictation via `webkitSpeechRecognition` where available (`chatMic`) and Enter to send. Opened by the `#fab` button (shown by `renderTabs` once loaded), the Assistant row of This device, or `a`. Opening it runs a quiet `assistantCheck(true)`; a missing function, a missing key or an older version shows a `.setupcard` that opens the setup sheet.
- The Anthropic key lives only in Supabase Edge Function secrets. Never put it in the app, `.env*` or the repo.

## UI
- Today has a Pipeline card (`pipeTodayCard`, side column after the to-dos): hot replies to answer first, warm deals (Talking, Demo booked, Proposal sent) due for a follow-up, calls due, new leads found today and the email state (off with Start sending, starts on a day, or sent today). Every row opens the lead. ## Conventions
- Dates are local `YYYY-MM-DD` strings. Never use UTC `toISOString()` for day keys.
- UI copy is plain, direct and second person.
- Colors come from the CSS tokens in `src/styles.css`, with light and dark both supported (auto, or forced via the Appearance setting, `data-theme` on `<html>`).
- Write one document at a time per path. Writes go through `setDoc`, `patchDoc` and `delDoc` in `main.js`.
- Never commit `seed/`, backups or `.env*`.

## Commands
- `npm run dev` runs locally at http://localhost:5173.
- `npm run build` produces the production build in `dist/` (service worker included). `npm run preview` serves it.
- `npm run icons` regenerates the icons in `public/`.
